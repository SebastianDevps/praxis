## Findings
- `hooks/pre-tool-use:355` (+ `hooks/lib.sh` praxis_is_spec_side) — `specs/<c>/decision.md` is spec-side, so the main thread can Write `verdict: APPROVE (human)` (or `APPROVE`) and the ship gate opens. Nothing checks who wrote it; `review_gate` only covers `review/round-*/*.md`. Probe: Write decision.md with `APPROVE (human)`, then `git push origin praxis/c` → hook output empty (allowed). The same Write with `ESCALATE` makes post-tool-use create `.praxis/needs-human/<c>`, the exact precondition `approve.sh` keys on. Fix: deny any Edit/Write whose content carries `APPROVE (human)` (only `approve.sh` writes it, by shell, not by tool), and restrict decision.md to the approver subagent (`agent_type`) — severity: blocking
- `hooks/pre-tool-use:259,276` + `hooks/lib.sh` praxis_active_change — `.praxis/active-change` is model-writable (`.praxis/*` is spec-side) and is the only key for the barrier, the cap and the ship gate. Write `nope` there: `[ -f "$ledger" ] || exit 0` makes all three gates silent. Probe: decision.md at ESCALATE, active-change=nope, `git push origin praxis/c` → allowed. Pointing it at another already-approved change also satisfies the floor for any source edit, since approval is keyed to the name, not to the edit. The ship gate should derive the change from the pushed `praxis/<x>` ref, not from a model-writable file — severity: blocking
- `hooks/pre-tool-use:172-187` (`ship_command`) — the tokenizer misses plain pushes of the branch, with no shell tricks needed. All probes returned allow: `git push origin praxis/c:main`, `+praxis/c:main`, `refs/heads/praxis/c`, `refs/heads/praxis/c:refs/heads/praxis/c` (the `*:praxis/c` pattern misses the `refs/heads/` form), `git push --all`/`--mirror`. Also unseen: `env git push`, `(git push …)`, `{ …; }`, `command`/`time`/`sudo git`, `bash -c "git push …"`, `eval`, `$(…)`, `git -c alias.p=push p`, `gh api …/pulls`, `gh pr merge`. The first group is inside the stated scope; the rest are the documented Bash class. Match on `${ref#+}` stripped of `refs/heads/`, on the left side of `:`, and on `--all|--mirror`; treat a segment whose argv[0] is not a plain git/gh binary but whose text contains `push` or `pr create` as deny — severity: blocking
- `hooks/pre-tool-use:300-305` (`review_gate`) — `agent_id` set means "a lens", but the builder is also a subagent. The builder can Write `review/round-N/<lens>.md` with `verdict: PASS` (absolute path to the main checkout) plus `decision.md` APPROVE, and the barrier and ship gate accept them. The gate checks "not the main thread", not "is this lens". Use `agent_type` against the lens named in the file, and deny the builder any write under `specs/*/review/` and `decision.md` — severity: important
- `hooks/lib.sh` praxis_round_lenses — the required set is `round-N/lenses` or the ledger `lenses:`, both orchestrator-writable and not `.md`, so not covered by `review_gate`. Drop the failing lens from the list and the round reads all PASS. Probe by reading code only; the contract says "+ ui when UI paths touched" and nothing enforces it. Likewise the ledger `round:` can be Written back to 0 (rework.sh's header admits "a counter the model resets is no cap"), which defeats the cap. Pin the lens list and the round in a hook-written file, or make post-tool-use snapshot `lenses` on first write and deny shrinking — severity: important
- `hooks/pre-tool-use:333-340` — marker protection is by case-sensitive prefix match on a path that `praxis_canonical_path` does not case-normalise (it appends the non-existent remainder verbatim; `.Praxis/Approved/c` came back with the attacker's case). The default macOS APFS volume is case-insensitive (probe: `touch .Praxis/Approved/zz` created `.praxis/approved/zz`). Write to `.Praxis/Approved/<c>` is not matched by the deny, is classed as a source edit, and is allowed silently once any change is approved (or on one `ask`). It forges the approval record for any change. Lower-case the relative path before the `case`, in both `pre-tool-use` and `praxis_is_spec_side` — severity: important
- Bash and the markers, stated exactly: `Bash` is only ever inspected for the ship gate. Under Bash the orchestrator can run `scripts/approve.sh <c>` (writes the approval marker; when `needs-human/<c>` exists it also writes APPROVE (human) and clears the marker), `scripts/rework.sh <c> x` (resets `round:` to 0, archives reviews and decision.md, clears needs-human), `touch .praxis/approved/<c>`, `sed -i` on the ledger. Nothing distinguishes the person from the model; `approve.sh` has no TTY check, env check or nonce. Combined with the first finding, the "ship override only for the person" claim holds only by prompt. Cheapest mechanical gain: deny Bash commands whose segments name `approve.sh`, `rework.sh` or `.praxis/(approved|needs-human)` unless the command is the slash-command's literal form — severity: important
- `scripts/approve.sh:70-76,88-94` — `--base` is printed unquoted from the ledger `base:` (or the `branch.<b>.praxisBase` git config worktree.sh set from its `$2`), and `$change` is unquoted in `git push -u origin praxis/%s`. Probe: `base: main; touch /tmp/PWNED #` printed `gh pr create --base main; touch /tmp/PWNED --head …`, which the orchestrator is told to paste. The Goal/title/body path is escaped correctly by `sh_dq` (`\ " $ \``; a Goal is one line, so no newline injection). Quote `base` and `change` through `sh_dq` or `printf %q` — severity: important
- `scripts/worktree.sh:38,87,95` — `base` (`$2`, model-supplied) goes to `git worktree add … "$base"` and `git config` without `--`/ref validation, so a value starting with `-` is read as an option. Change names also allow a leading `-` and whitespace/`;` (only `/`, `..`, leading `.` are rejected); every use is quoted, so no injection found, only option confusion. Validate with `git check-ref-format --branch` and `^[a-z0-9][a-z0-9-]*$` — severity: minor
- `scripts/worktree.sh:66-69` — the seeded `.praxis/approved/<c>` in the worktree is a copy, not an approval surface the model can write (Write to it is denied after the re-root and the seed needs the main marker). It is a stale second copy: removing the main marker (there is no revoke command) leaves the builder approved. Also `post-tool-use` does not re-root, so a builder edit in a worktree writes the main marker on its own first allowed edit. Consistent with the main-checkout behaviour, noted — severity: minor
- `hooks/hooks.json:54` — matcher omits `NotebookEdit`, which the script's tool list handles. A `.ipynb` write skips the floor and the marker deny. Dispatch gate keys only on `subagent_type` `builder`: a `general-purpose`/`engineer` agent doing the build bypasses the barrier and the cap — severity: minor
- No secrets in the diff, fixtures or `gh pr create` text (the body is two repo paths and a round number). `hooks/post-tool-use` reads `decision.md` from disk after any edit that targeted it, not the edit's content; that is fine, and the only consequence is that the model's forged verdict is trusted (first finding). The `gh` stub in evals was not reviewed for PATH precedence — see questions below.
